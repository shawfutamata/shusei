# 課金・契約アーキテクチャ

更新日: 2026-08-27

## 採用する形

GIVE HUBは**無料で使えるWebサービス**を本体とし、一部の機能だけを有料会員向けにする（線引きは `docs/pricing-plan-ja.md`）。iOS・Android版は、会員が同じアカウントで使う無料のコンパニオンアプリとして提供する。

契約・決済はアプリの外（Web）だけで行う。**アプリには、その人がいま使える機能しか出さない。** 無料会員には有料機能の画面自体を表示せず、グレーアウトや鍵アイコンも出さない。

```text
案内・営業・契約・決済・解約
        ↓  アプリ外だけで実施
Webサービスの会員権限を更新
        ↓
iOS / Androidはログイン後に権限を確認
        ↓
投稿・紹介・名刺・通知を利用
```

## アプリ内に置かないもの

- 料金、プラン比較、無料体験の申込
- 「Webで申し込む」「ブラウザで支払う」などの購入CTA
- Stripeなどの決済画面、WebView、外部決済リンク
- 未契約者を決済ページへ誘導する文言
- 有料ポイントや有料ランクアップ

ログインできない利用者には「このメールアドレスには利用権限がありません。運営窓口へお問い合わせください」とだけ表示し、購入先は案内しない。

## Web側で持つ契約状態

Web側の会員データに次の権限情報を持たせる。データ構造とログイン時の判定は実装済みで、決済サービス確定後はWebhookまたは運営管理画面から状態を更新する。

- `membership_status`: `active` / `past_due` / `canceled` / `invited`
- `membership_source`: `direct_contract` / `organization_contract`
- `current_period_end`
- `organization_id`（法人・会場単位契約の場合）

決済Webhookまたは運営管理画面がこの権限だけを更新する。モバイルアプリは決済サービスへ直接接続せず、ログインAPIから返る利用可否だけを見る。

## ストア審査での説明

- 有料Webサービスが本体であり、アプリは既存契約者向けの無料コンパニオンである。
- アプリ内で購入、申込、アップグレード、価格表示、外部購入への誘導を行わない。
- 審査用の有効なテストアカウントを用意する。
- 法人・会場単位で直接販売する場合は、その契約形態も審査メモに明記する。

Appleはデジタル機能をアプリ内で販売する場合は原則としてアプリ内課金を要求する。一方、購入や外部購入CTAのない有料Webツールの無料コンパニオンはガイドライン3.1.3(f)、組織・グループへ直接販売するサービスは3.1.3(c)の対象になり得る。最終的な販売対象が個人契約か組織契約かを、申請前に確定する。

Google Play版も同じく「閲覧・利用専用」に統一する。日本向け外部決済リンクプログラムは手数料と追加実装が伴うため利用しない。

## 会員紹介と価格表示の分離

会員紹介（招待）では会費が無料になる月が発生するが、**アプリにはその話を出さない**。取得口を分けてある。

- `GET /api/invite`（アプリ・Web共用）: 招待リンクと人数だけ。金額・割引を含めない
- `GET /api/entitlements`（アプリ・Web共用）: 使えるかどうかと件数だけ。金額・割引を含めない
- `GET /api/referral`（Webのみ）: 無料月、上限、今年の残りを含む

アプリのマイページには「仲間を招待する」と招待人数だけを出す。詳しくは `docs/referral-program-ja.md`。

## 申請前の禁止チェック

- [ ] アプリの全画面に価格・購入リンクがない
- [ ] アプリの招待画面に無料月・割引の文言がない（`/api/invite` だけを使っている）
- [ ] 無料会員のアプリに有料機能の画面・鍵アイコン・アップグレード導線がない
- [ ] App Store / Google Playの説明文に外部購入案内がない
- [ ] ログイン失敗時に決済ページへ遷移しない
- [ ] プライバシーポリシーやヘルプから決済ページへ連鎖しない
- [ ] 審査メモでビジネスモデルを正直に説明している
- [ ] Webサービス単体でも契約・利用できる
- [ ] アプリはストアから無料で配布する
